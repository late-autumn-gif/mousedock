# A7 Ultra 与 M2 V5 HE 的 2.4G 电量适配

两份 v1.1.8 反馈报告各采样三轮，安全模式关闭。两台设备都枚举成功，原版均无匹配的专用查询，报告没有电量响应帧。报告中的键盘 HID 产品串为通用名称，M2 V5 HE 是反馈者补充的商品型号。

| 设备 | 反馈报告的通道 | 当前读取行为 |
| --- | --- | --- |
| MCHOSE A7 Ultra | `5253:1020`，`MI_02/COL_02`，`FF01/0001`，Input/Output/Feature 均 65 字节，Feature 含 ID `0x11` | 同一物理实例内用 `11/F9` 查询。核验命令、解码后的厂商和 `0x0011` 型号、2.4G 在线位、电量范围及充电字段。 |
| MonsGeek M2 V5 HE | `3151:5038`，`MI_01/COL_05` 的 32 字节 Input 事件，以及 `MI_02` 的 `FFFF/0002`、65 字节 Feature、ID `0x00` | 优先监听在线 `05/88` 电量事件。未收到有效事件时，才在同实例的 Feature 集合查询 `F7` 接收器状态。 |

迈从的本地 M HUB 驱动产物列出 A7 Ultra 型号 `0x0011`，并通过 Feature 的 `11/06` 获取设备信息。传输时命令和载荷按字节异或 `FF`，与仓库既有 `11/F9` 报告格式一致。[MCHOSE M HUB](https://www.mchose.store/pages/mchose-hub)

2026-11-12 反馈者确认 A7 Ultra 在测试包上通过实机测试。键盘新报告三轮均成功打开事件集合，每轮约 800 ms 内没有可解析的电量事件。该报告同时确认了 `MI_02` 的 Feature 集合，未包含 `F7` 实机应答。

[MonsGeek V4 官方驱动](https://app.monsgeek.com/) 的构建 `index.1e076e39.js` 将 `3151:5038` 列为 2.4G 接收器，并通过 `___dongleCheck24GStatusByF7` 读取电量。直发 `F7` 并以零填充。去除 Windows 的 Report ID 后，载荷第 1 字节是键盘百分比，第 3 字节为零表示键盘在线，第 5 字节为 1 表示可发送，第 6 字节 1 或 3 表示包含键盘，第 8 字节为 1 表示 RF 引导模式。以上均为从零开始的索引。

[公开的 MonsGeek/Akko 协议实机研究](https://github.com/echtzeit-solutions/monsgeek-akko-linux/blob/master/docs/PROTOCOL.md#22-24ghz-wireless-dongle) 记录了接收器 SRAM 中的电量缓存。它对部分状态字节的解释与 V4 驱动不同，本次按 V4 的键盘在线判定处理。两次连续有效查询返回相同且非零的百分比才采用，显示为待刷新，来源注明接收器缓存。查询应答没有电量采样时间，不据此推断充电、满电或商品型号。零可能是接收器上电后的初始值，单靠该缓存无法确认 0%。

两条路径仅在正常发现流程按物理实例读取，要求该实例具有唯一匹配集合。安全模式或识别关闭时跳过。每轮读取受时间限制，原生调用超时后丢弃晚到结果。读不到时采集层返回未知，已有读数由应用的通用机制标为待刷新。导出诊断只保留用于回放的协议字节，其他输入内容不保存。

实机复测保持键盘在 2.4G 档，唤醒后刷新。如读到数值，记录厂商驱动的同期读数，并观察键盘关机后缓存的显示。若仍为 `—`，使用新包导出报告，检查 `MonsGeekDongleStatus` 的发送、读取与状态校验阶段。

首轮 Windows x64 构建通过，协议与集成测试共通过 16,406 项断言。打包程序重放原始报告的六轮样本均成功，保留采集时的未知电量。原始报告和测试包仅保存在本地。

F7 测试包通过 Windows x64 构建与 16,428 项离线断言。本轮新增 22 项，覆盖官方请求布局、异常状态、响应中断、实例隔离、新事件优先、缓存显示及诊断回放。测试包成功重放键盘新报告的三轮失败记录。随后用户确认 A7 Ultra 和 M2 V5 HE 均通过 2.4G 实机测试。该确认覆盖测试包的使用结果，未提供本轮原始 F7 回包、对照百分比或充电样本。
