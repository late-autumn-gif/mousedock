# 竹林鸟玄武 ZG2：设备识别与电量调查

日期：2026-11-03。分析目标为用户提供的本地安装目录 `D:\竹林鸟玄武驱动`，没有执行安装程序或修改耳机固件。

## 当前设备

Windows 已枚举到 `4C4A:4155` 的 USB 复合设备，产品为 `ZhuAudio ZG2`，含音频输出、麦克风及 MI_03 Consumer Control HID。用户确认当前使用 2.4G USB 接收器。

本机 HID 元数据只读查询结果：用法页/用法 `000C/0001`；Input/Output/Feature 长度 `3/0/0`。原来 MouseDock 只接受 Generic Desktop 下的鼠标、键盘和手柄集合，因此跳过它。1.3.3 对此 VID/PID 的 Consumer Control 集合补充耳机识别；其它消费控制设备不因此被归类为耳机。

## 官方程序“找不到设备”的直接原因

目标主程序 `ZhuAudio USB Device.exe` 的 SHA-256 为 `5d6c4f208c2d6fa2f0d757f624fceba6f7e067c4fe5700fbb22591f57a7832ac`。它导入 `xii_ecd_api.dll` 的 `getDeviceCount`、`_exec_usb_encrypt`、`_hid_trans_data` 等接口。

对原生 PE 使用 pefile 和 Capstone 做静态分析；这些结果不是 REA MCP Evidence。没有已连接的 REA 原生分析服务，因此使用技能允许的本地分析路径，没有安装或修改 MCP 配置。

- `xii_ecd_api.dll` RVA `0x1A530` 的设备表读取器访问 RVA `0x215D8`。
- 两条 12 字节记录为 `90530000 E2A00000 0300 0200` 与 `90530000 E3A00000 0300 0200`。
- 设备计数路径 RVA `0x23D0` 在使用前将 VID、PID 与 `0x579B` 异或，得到 `040B:F779`、`040B:F778`；接口号 3，报告 ID 2。
- 这两条记录不包含当前接收器 `4C4A:4155`。具体产品代次关系没有确认，不据此断言耳机损坏或其完整硬件能力。

使用 Frida 对本地官方主程序进行了有时限的启动与只读日志插桩。没有替换函数返回值、改写设备表或试发未知命令。第一次启动窗口约 30 秒，记录 615 条事件；第二次约 5 秒，明确记录：

```text
hid_enum_intf_rptid(vid=040B, pid=F779, iface=3, reportId=2) -> NULL
hid_enum_intf_rptid(vid=040B, pid=F778, iface=3, reportId=2) -> NULL
getDeviceCount(0x37DDE8EF) -> 0
```

同时观察到程序能枚举当前 `4C4A:4155` 的 HID 节点并读取集合属性，但没有将其纳入受支持设备计数。单独正常启动程序时，实际窗口显示“温馨提示：找不到设备”。两次插桩均已卸载、分离，并终止本次拥有的跟踪进程。

另外发现桌面驱动快捷方式指向不存在的 `D:\竹林鸟玄武驱动XiiSound`。该快捷方式已修正到实际安装目录；修正后官方程序仍会因上述设备匹配条件显示“找不到设备”，所以路径错误和设备匹配错误是两个问题。

## 电量证据与限制

主程序与 SDK 中已定位 HID Output/Input、Feature 封装及音效配置相关代码，但当前跟踪未捕获到针对 `4C4A:4155` 的有效电量查询/应答。找到的 `09` 请求及 16 字节校验载荷没有被证明包含电量，不能从中任选 0–100 的字节作为百分比。

当前 HID 集合没有 Output/Feature 报告，只有 3 字节输入；这能说明常规 HID 请求通道在本机不可用，不能证明固件不存在其它 USB、音频驱动、蓝牙或私有通道。只改 VID/PID 以强行绕过官方程序的检查，也不能创造缺失的报告和电量能力。

MouseDock 现可发现该耳机，并明确显示电量未知。稳定、实时电量读取尚未实现；后续需要匹配当前接收器的协议/固件证据，或验证其它实际可用通道。不得以缓存、随机值或声音/按键状态冒充电量。
